**决策:**

### 架构决策 [认证机制重构]
*   **决策时间**: 2025-07-19 19:55:00
*   **决策**: 将后端认证机制从基于 Session 的有状态认证，完全重构为基于 JWT 的无状态认证。
*   **理由**:
    1.  **API规范对齐**: `api-spec.md` 明确要求使用JWT。
    2.  **无状态与可扩展性**: JWT是无状态的，更适合分布式和微服务架构，便于未来扩展。
    3.  **解耦**: 客户端不再依赖服务端的Session状态，降低了前后端的耦合度。

### 未解决的后端Bug：登出接口返回500
**日期:** 2025-07-20

**现象:**
- 前端调用登出接口 (`/api/v1/auth/logout`) 时，后端返回 `500 Internal Server Error`。
- 通过断点调试发现，后端的 `logoutHandler` 函数根本未被调用。

**分析过程:**
1.  **初步分析**: 怀疑是 `logoutHandler` 内部因缺少认证信息而 panic。
2.  **修正分析**: 用户反馈 `logoutHandler` 未被调用，推断问题出在中间件链。
3.  **深入分析**: 发现 `/logout` 被错误地注册为公共路由。尝试将其移至私有路由组，但用户反馈问题依旧存在。

**当前状态:**
- **未解决**. 这是一个深层次的后端问题，可能与 Gin 框架的内部机制、中间件的执行顺序或某些未知的冲突有关。
- **决策**: 根据用户指令，暂时搁置此 bug，优先完成前端认证流程的整体实现。此 bug 已记录，待后续由后端专家进行专题攻关。

### 架构决策 [章节管理API路由重构]
*   **决策时间**: 2025-07-20 22:16:00
*   **决策**: 采纳以资源为中心的扁平化API路由方案，以更好地对齐前端业务逻辑，并简化路由管理。
*   **理由**:
    1.  **对齐前端业务**: 前端页面URL（如 `/chapters?workId=...` 和 `/chapters/[id]/edit`）表明其业务逻辑是以“章节”为中心，而非严格的父子嵌套。扁平化的API路由 (`/api/v1/chapters`) 直接服务于前端的数据请求模式，降低了前后端对接的复杂性。
    2.  **简化管理**: 维护单一、扁平的 `/api/v1/chapters` 路由组比管理混合式或纯嵌套式路由的管理成本更低，API结构更清晰。
    3.  **集中安全控制**: 所有权限验证逻辑（用户是否拥有章节所属的作品）将被统一封装在 `ChapterAuthMiddleware` 中。该中间件负责处理基于 `work_id`（来自查询参数或请求体）或 `chapter_id`（来自URL路径）的权限校验，确保了逻辑的内聚和安全。
    4.  **高扩展性**: 该设计易于未来扩展，例如支持按其他维度（如分卷 `volume_id`）进行查询，而无需改动整体路由结构。

*   **最终路由设计**:
    *   `GET /api/v1/chapters?work_id={work_id}`: 获取指定作品的章节列表。
    *   `POST /api/v1/chapters` (请求体中包含 `work_id`): 创建新章节。
    *   `GET /api/v1/chapters/{id}`: 获取单个章节详情。
    *   `PUT /api/v1/chapters/{id}`: 更新单个章节。
    *   `DELETE /api/v1/chapters/{id}`: 删除单个章节。

### 架构决策 [最终的、分层感知的、基于组合的统一服务架构蓝图]
*   **决策时间**: 2025-07-30 18:15:00
*   **决策**: 采纳最终的、分层感知的、基于组合的统一服务架构蓝图，作为后续所有模块重构的唯一标准。
*   **理由**:
    1.  **分层不可动摇**: 新架构严格遵循 `contracts`, `repositories`, `services`, `controllers`, `apps` 的既定分层，确保了系统的清晰结构和可维护性。
    2.  **抽象通过组合**: 通过组合更小的、功能单一的接口来获得模块接口的能力，避免了顶层泛型接口的复杂性，使接口更加灵活和易于理解。
    3.  **复用通过嵌入**: 模块的实现通过嵌入一个通用的基类实现来复用代码，这种方式比继承更加灵活，避免了继承带来的紧耦合问题。
    4.  **借鉴成功模式**: 新模式与已有的"模块化自注册"模式在设计哲学上保持高度一致，确保了架构的一致性和延续性。
