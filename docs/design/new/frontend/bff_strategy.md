# BFF 设计策略 (最终版 - 安全核心)

## 1. 背景与核心安全目标
本项目采用 BFF (Backend for Frontend) 模式。经过深入讨论，我们明确其核心目标不仅在于架构解耦，更在于构建一个坚实的安全屏障。BFF 必须达成以下两个核心安全目标：

1.  **防止密钥暴露 (Secret Protection):** 任何与后端或其他服务通信所需的敏感凭证（API Keys, Secrets）绝对不能暴露在客户端（浏览器）。
2.  **防止爬虫抓取 (Anti-Scraping):** 必须有有效机制来抵御恶意的、自动化的 API 请求，保护我们的数据和服务器资源。

## 2. BFF 安全架构设计
为了实现上述目标，我们的 BFF 将不仅仅是一个简单的代理，而是一个**安全增强型网关**。所有从前端发起的 API 请求，都将指向 BFF，并在 BFF 层经过严格的安全检查后，才能被转发到后端。

### 2.1 方案一：防止密钥暴露
BFF 是解决此问题的完美方案。

-   **机制:** 敏感密钥将作为**服务端环境变量**存储在 Next.js 服务器中。这些变量对客户端是完全不可见的。
-   **流程:** BFF 在接收到前端请求后，会在服务端将密钥附加到转发给后端 API 的请求头中。
-   **结论:** 此方案 **100%** 解决了密钥在客户端暴露的风险。

### 2.2 方案二：防止爬虫抓取
我们将组合使用以下两种机制，在 BFF 层构建纵深防御。

1.  **强制认证 (Authentication Enforcement):**
    -   **描述:** BFF 将作为认证的第一道关卡。它会校验所有请求是否包含一个由 `next-auth` 签发的、合法的用户会话凭证 (JWT)。
    -   **效果:** 任何匿名的、未经认证的请求都将被 BFF **直接拒绝**，使其无法触及后端 API。这能有效拦截绝大多数简单爬虫。

2.  **速率限制 (Rate Limiting):**
    -   **描述:** 这是对抗高级自动化爬虫**最有效**的手段。我们将引入速率限制中间件（如 `@upstash/ratelimit`），对请求频率进行控制。
    -   **效果:** 我们可以设定“每个登录用户每分钟最多请求 100 次 API”等规则。一旦超出限制，BFF 将直接返回 `429 Too Many Requests` 错误，有效遏制恶意的高频抓取。

## 3. 最终工作流
我们的前端代码（包括由 `Orval` 自动生成的客户端）将统一请求 BFF 的入口（例如 `/api/proxy/...`）。

**请求流程示意:**
```
前端组件
   |
   v
axios (baseURL: '/api/proxy')
   |
   v
BFF 代理层 (Next.js Server)
   |
   +-- 1. 安全检查 (强制认证 + 速率限制)
   |
   +-- 2. [若通过] 附加服务端密钥 (如需要)
   |
   v
后端 API (e.g., http://localhost:8080/api/v1)
```

## 4. 结论
此安全增强型 BFF 架构，完美地满足了我们对**防爬虫**和**防密钥暴露**的核心安全需求。它在 `Orval` 自动化带来的高效率和强大的安全保障之间取得了理想的平衡，是符合我们项目长期利益的最佳实践。
