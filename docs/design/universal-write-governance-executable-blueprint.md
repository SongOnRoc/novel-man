# 通用写入治理可执行实施计划（Executable Blueprint）

> 基于《事件触发的模块自治更新设计》形成工程可执行方案。本文仅做实施拆解，不改变原架构机制。

## 0. 文档定位（Canonical）

- 主文档（canonical）：`docs/design/universal-write-governance-executable-blueprint.md`
- 本文为“通用写入治理可执行实施计划”的唯一维护版本。
- 历史文件 `docs/design/universal-write-governance-implementation-plan.md` 仅保留迁移说明，不再承载实施细节。

## 1. 文档目标与范围

### 1.1 目标

将原设计主链路拆解为研发可直接认领、可量化验收、可回滚的执行方案：

**事实变更 -> 发布事件 -> 队列调度 -> 模块重算 -> 模块更新 -> Outbox通知**

### 1.2 范围

- 覆盖 Phase A/B/C/D 的实施目标、任务、里程碑、交付物、风险与回滚。
- 覆盖跨阶段治理：测试、运维、数据一致性、安全审计。
- 覆盖验收标准映射与建议排期、角色分工。

### 1.3 严格边界

- 不引入与原设计冲突的新机制。
- 不引入分布式事务，保持最终一致性。
- 不允许读请求触发重算。
- 不扩展前端无关需求。

---

## 2. 实施总览（阶段划分）

| 阶段 | 核心目标 | 关键里程碑 | 阶段退出条件 |
| --- | --- | --- | --- |
| Phase A | 事件基础设施落地 | Publisher/EventManager/Queue 联调通过 | 去重、重试、DLQ 全链路可运行 |
| Phase B | Works 首批迁移 | Works Consumer 上线 + GET 触发重算下线 | 查询链路零写入，幂等回放通过 |
| Phase C | 多模块推广 | 六模块逐个接入并完成门禁 | 无跨模块直写，压测达标 |
| Phase D | Outbox 与可观测性 | 通知全通道 + 追踪与告警上线 | 通知故障不阻塞主链路 |

---

## 3. 分阶段执行计划

### 3.1 Phase A：事件基础设施（Publisher/EventManager/Queue，含去重/重试/DLQ）

#### 目标

建立统一事件触发基础能力，确保“事实提交成功后触发”成为唯一入口，并具备去重、重试、DLQ、并发治理能力。

#### 任务清单（可直接认领）

1. 定义并落库核心对象：`FactEvent`、`QueueTask`、`DedupRecord`、`DLQRecord`、`OutboxMessage`。
2. 实现 `FactEvent Publisher`：仅在事务提交成功后发布事件。
3. 实现 `EventManager`：仅做事件路由和任务生成，不做业务重算。
4. 实现 `QueueScheduler`：入队、去重、重试、死信、并发上限。
5. 固化键策略：
   - 去重键：`event_id + module`
   - 分区键：`aggregate_type + aggregate_id + module`
6. 提供 DLQ 回放工具与运行手册。

#### 里程碑

- M-A1：核心事件对象与存储模型完成。
- M-A2：发布器 + 事件管理器 + 队列联调通过。
- M-A3：故障注入场景下重试与 DLQ 行为符合预期。

#### 交付物

- 事件基础设施设计与实现文档。
- 队列参数基线（并发、退避、重试阈值）。
- 回放与故障演练手册。

#### 可量化验证点

- 同一 `event_id` 重放 100 次，去重生效且结果一致。
- 超阈值失败任务进入 DLQ 成功率 100%。
- 压测下队列无失控堆积，消费延迟维持阈值内。

#### 风险与回滚

- 风险：去重失效导致重复消费。
  - 回滚：临时关闭消费者，仅保留事件入库与审计。
- 风险：重试风暴冲击数据库。
  - 回滚：下调并发阈值并提前入 DLQ。

---

### 3.2 Phase B：Works 模块首批迁移（下线 GET 触发重算）

#### 目标

将 Works 迁移为纯事件触发重算，彻底移除 GET 链路写入触发。

#### 任务清单（可直接认领）

1. 接入 Works Consumer，建立事件订阅与重算流程。
2. 下线 `works` 读请求触发重算路径。
3. 补齐 Works 最小补丁更新接口，控制写放大。
4. 建立 Works 专项幂等回放测试。
5. 执行灰度发布与观察（失败率、时延、连接池波动）。

#### 里程碑

- M-B1：Works 事件消费链路打通。
- M-B2：GET 触发重算路径下线完成。
- M-B3：灰度通过并全量切换。

#### 交付物

- Works 迁移清单与开关策略。
- 查询禁写验证报告。
- Works 回放一致性报告。

#### 可量化验证点

- 查询压测期间，读接口链路数据库新增写入 = 0。
- 同一 `event_id` 在 Works 回放 100 次，结果一致率 100%。
- 高频更新下连接池与队列无明显惊群抖动。

#### 风险与回滚

- 风险：残留读中写路径。
  - 回滚：恢复迁移开关并保留审计追踪。
- 风险：重算耗时过高。
  - 回滚：降低并发、切换批处理窗口。

---

### 3.3 Phase C：多模块推广（chapters/characters/worldview/drafts/settings/prompts）

#### 目标

在 Works 模板基础上推广到六模块，保持模块自治，禁止跨模块直写。

#### 任务清单（可直接认领）

1. 建立六模块事件矩阵（订阅事件、重算规则、更新对象）。
2. 按批次接入消费者（建议顺序：chapters -> characters -> worldview -> drafts -> settings -> prompts）。
3. 复用统一幂等模板与重试策略。
4. 执行模块边界审计，清除跨模块写入。
5. 每模块上线前执行三项门禁：事件矩阵检查 + 幂等回放 + 压测。

#### 里程碑

- M-C1：六模块事件矩阵评审通过。
- M-C2：六模块消费者全部接入上线。
- M-C3：跨模块直写违规项清零。

#### 交付物

- 模块事件矩阵总表。
- 各模块接入记录与上线报告。
- 模块级压测与回放报告。

#### 可量化验证点

- 六模块全部通过三项门禁。
- 跨模块直写违规数 = 0。
- 重复重算率与失败率满足设定阈值。

#### 风险与回滚

- 风险：模块依赖不清导致连锁故障。
  - 回滚：按模块独立熔断与回退。
- 风险：推广过快导致验证不足。
  - 回滚：冻结下一批次，仅修复当前批次。

---

### 3.4 Phase D：Outbox 通知与可观测性（全链路追踪与告警）

#### 目标

完成通知链路与运维可观测能力，保障“通知故障不阻塞主链路”。

#### 任务清单（可直接认领）

1. 接入 Outbox 多通道：站内通知、WebSocket、外部 MQ。
2. 实现 Notifier Worker 通道级重试与死信。
3. 贯通追踪字段：`trace_id`、`event_id`、`task_id`。
4. 建立关键指标看板：吞吐、失败率、重试率、DLQ 增速、P95/P99。
5. 配置告警规则并完成故障演练（含值班处置流程）。

#### 里程碑

- M-D1：Outbox 全通道联通。
- M-D2：指标与告警上线。
- M-D3：故障演练通过。

#### 交付物

- 通知运行手册。
- 可观测性指标清单与告警规则。
- 演练报告与恢复记录。

#### 可量化验证点

- 任一通知通道故障时，主更新链路成功率保持稳定。
- 可按 `trace_id` 完整追踪“事实提交 -> 通知下发”全过程。
- 告警触发后 5 分钟内可定位故障组件。

#### 风险与回滚

- 风险：通知积压反向影响主链路。
  - 回滚：降级非关键通知通道。
- 风险：观测盲区导致恢复慢。
  - 回滚：启用应急高等级日志与人工巡检。

## 4. 跨阶段治理

### 4.1 测试治理

1. 单元测试：Publisher、EventManager、Queue 去重/重试逻辑。
2. 集成测试：主链路时序、模块消费、Outbox 通知。
3. 回放测试：同事件重复回放一致性。
4. 压测门禁：高频事件下吞吐、失败率、时延、连接池稳定性。

### 4.2 运维治理

1. 固化“灰度 -> 观察 -> 全量”发布流程。
2. 建立模块开关、通道降级开关、回放开关。
3. 建立 DLQ 日常回放与清理 SOP。

### 4.3 数据一致性治理

1. 消费者统一基于最新事实快照重算。
2. 消费前强制去重索引检查，确保幂等。
3. 事件/任务/通知全链路保留追踪字段。

### 4.4 安全审计治理

1. 关键操作留痕：操作者、来源、时间、请求追踪。
2. 敏感字段脱敏与最小化记录。
3. 读接口禁写纳入自动化门禁与评审清单。

## 5. 验收标准映射（逐条对应原设计）

| 原设计验收项 | 实施计划映射动作 | 验证方法 | 对应阶段 |
| --- | --- | --- | --- |
| 查询行为不会触发任何更新 | 下线 GET 触发重算 + 读链路禁写门禁 | 查询压测 + SQL 审计 | Phase B |
| 每次更新都可追溯到事实事件 | trace/event/task 三键贯通 | 链路抽样追踪 | Phase A/D |
| 高频事件下无明显重复重算 | 去重键 + 幂等消费模板 | 同事件回放 100 次 | Phase A/C |
| 无惊群导致数据库抖动 | 分区串行 + 并发上限 + 退避重试 | 高并发压测 + 连接池指标 | Phase A/C |
| 通知链路故障不影响主流程 | Outbox 异步解耦 + 通道降级 | 故障注入演练 | Phase D |
| 查询压测期间数据库无新增写操作（工程补充） | Works 读中写路径下线 | 压测窗口写统计 | Phase B |
| 同一 `event_id` 重放 100 次结果一致（工程补充） | 回放工具 + 幂等索引 | 回放报告 | Phase A/B/C |
| 高频更新下队列无惊群抖动（工程补充） | 调度参数与并发治理 | 队列+数据库联合压测 | Phase A/C |
| 通知通道故障时主链路成功率稳定（工程补充） | Outbox+Notifier 故障隔离 | 演练报告 | Phase D |

## 6. 建议排期与资源角色分工

### 6.1 建议排期（10 周示例）

1. 第 1-2 周：Phase A（基础设施实现与联调）。
2. 第 3-4 周：Phase B（Works 迁移与读链路禁写）。
3. 第 5-8 周：Phase C（六模块分批推广，每批 1-2 模块）。
4. 第 9-10 周：Phase D（Outbox 全通道、观测告警、演练验收）。

### 6.2 资源角色分工

| 角色 | 职责 |
| --- | --- |
| 技术负责人（TL） | 架构守护、阶段评审、风险决策 |
| 平台后端 | Publisher/EventManager/Queue/DLQ 基础设施 |
| 业务后端 | Works 与多模块 Consumer 接入、重算逻辑 |
| SRE/运维 | 指标、告警、发布与演练流程 |
| QA | 回放测试、压测、验收报告 |
| 安全审计 | 留痕规范、敏感信息审计、合规检查 |

### 6.3 里程碑评审节奏

1. 每阶段结束执行一次阶段退出评审。
2. 未达到退出条件不得进入下一阶段。
3. 所有验收结论需附证据（测试报告、压测报告、演练记录）。

---

## 7. 执行准则（统一口径）

1. 仅“事实提交成功”可触发事件。
2. 事件管理器与队列不承担业务重算。
3. 模块消费者仅更新本模块数据，禁止跨模块直写。
4. 去重、重试、DLQ 为默认能力，不可省略。
5. 通知通过 Outbox 异步下发，故障不阻塞主链路。

**统一执行口径：事实变更 -> 发布事件 -> 队列调度 -> 模块重算 -> 模块更新 -> Outbox通知。**
