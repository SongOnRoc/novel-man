## 1. 概述

### 1.1. 背景与问题陈述

当前，我们的写作应用内置的AI功能仅为一个基础框架，其API结构分散、核心逻辑缺失、且前端功能硬编码，远不能满足用户对于智能化写作辅助的期望。为了提升产品核心竞争力，为用户提供真正实用、高效的AI写作工具，我们需要对现有AI功能进行一次全面的重构和升级。

**核心问题:**
*   **功能割裂:** 用户需要在不同入口使用不同的AI功能，体验不连贯。
*   **功能缺失:** 缺乏对提示词（Prompt）的有效管理和复用能力，限制了高级用户的创造力。
*   **扩展性差:** 无法动态增减AI助手类型，也无法支持用户自定义AI模型，难以适应快速发展的AI技术生态。

### 1.2. 目标与价值

本次迭代旨在构建一个统一、可扩展、用户驱动的AI助手平台。

*   **业务目标:**
    *   将AI助手打造为产品的核心功能之一，提升用户活跃度和付费转化率。
    *   通过提供强大的自定义功能，吸引并留住高级创作者用户。
*   **产品目标:**
    *   **统一体验:** 将所有AI生成功能整合至统一的API和UI入口。
    *   **赋能用户:** 提供强大的提示词库管理功能，让用户沉淀和复用创作智慧。
    *   **开放灵活:** 支持用户配置自己的AI模型，满足个性化和专业化的需求。

### 1.3. 成功指标

*   **核心指标:**
    *   AI助手功能日活跃用户数（DAU）提升 50%。
    *   用户创建的自定义提示词总量超过 1,000 条。
*   **辅助指标:**
    *   AI功能接口（`/api/generate`）日均调用次数。
    *   用户自定义AI模型配置创建数。
    *   用户满意度调研中，对AI助手功能的评分达到 4.5/5.0。

### 1.4. 项目范围

本次项目将分两个阶段进行。

*   **V1.0 (MVP) 范围:**
    *   后端：实现统一生成接口 (`/api/generate`) 和提示词管理接口 (`/api/prompts`)。
    *   前端：重构AI服务，开发提示词管理界面，并实现基础的助手选择功能。
    *   功能：支持内置的AI工具（如扩写、缩写），支持用户创建、编辑和删除自己的提示词。

*   **V2.0 (未来迭代) 范围:**
    *   高级功能：支持用户自定义AI模型（URL, Key, Model Name）。
    *   高级功能：在AI助手面板中直接调用和使用提示词库中的内容。

## 2. 用户画像与场景

### 2.1. 用户画像

*   **角色:** 李想，一名网络小说作家。
*   **背景:** 他每天需要产出数千字的内容，经常面临灵感枯竭、情节卡壳、或需要对初稿进行润色的挑战。
*   **痛点:**
    *   "我有一些常用的指令（Prompt）来让AI帮我描写环境或深化角色对话，但每次都要重新输入，非常麻烦。"
    *   "应用里内置的几个AI工具太基础了，我想用我自己付费的、更强大的AI模型来写作。"
    *   "不同功能入口分散，我希望有一个统一的、随时可以呼出的AI助手。"

### 2.2. 用户故事 (User Stories)

| 史诗 (Epic) | 用户故事 | 优先级 |
| :--- | :--- | :--- |
| **核心AI生成** | 作为一个作者，我想要一个统一的AI助手入口，无论我是想扩写、缩写还是进行创意写作，都能在这里完成，以便简化我的工作流程。 | **高** |
| | 作为一个作者，我想要从一个清晰的列表中选择不同类型的写作助手（如“通用助手”、“技术写作助手”），以便针对不同场景获得最合适的AI支持。 | **高** |

## 3. 功能需求 (V1.0)

### 3.1. FRD-1: 统一AI生成服务

*   **需求描述:** 所有AI文本生成功能都通过一个统一的入口和后端接口进行处理。
*   **功能点:**
    *   **3.1.1 (后端):** 实现 `GET /api/generate` 接口，用于返回所有可用的、预设的助手类型列表（如：默认助手、创意写作助手）。
    *   **3.1.2 (后端):** 实现 `POST /api/generate` 接口，作为所有AI生成请求的唯一入口。该接口能根据传入的 `assistant_type` 或 `prompt_id` 执行相应的生成逻辑。
    *   **3.1.3 (后端):** 废弃所有旧的、分散的 `/ai/*` 接口。
    *   **3.1.4 (前端):** AI服务 (`ai.service.ts`) 需要被重构，所有AI调用逻辑统一到一个 `generate()` 函数。
    *   **3.1.5 (前端):** 在AI助手UI中，提供一个下拉选择框，其选项通过调用 `GET /api/generate` 动态填充，让用户可以选择助手类型。用户的选择应被本地持久化，在所有AI功能中全局生效。如果用户未做选择，则使用系统默认助手。

### 3.2. FRD-2: 提示词库管理

*   **需求描述:** 为用户提供一个可视化的界面，用于完整地管理（增删改查）自己的提示词。
*   **功能点:**
    *   **3.2.1 (后端):** 实现 `/api/prompts` 的完整CRUD接口，遵循分析报告中的API规范。
    *   **3.2.2 (后端):** 创建 `prompts` 数据库表，并定义相应的GORM模型。
    *   **3.2.3 (后端):** 接口操作需要与用户身份绑定，确保数据隔离。
    *   **3.2.4 (前端):** 创建一个新的UI界面（可以是独立页面或模态框），用于展示用户的提示词列表。列表中每个条目都应清晰地展示其关联的标签。
    *   **3.2.5 (前端):** 在提示词库界面，提供“新建”、“编辑”、“删除”按钮，并开发相应的表单，允许用户输入标题、内容和标签。
    *   **3.2.6 (前端):** 提示词库界面需要提供基于标签的筛选功能，允许用户快速找到特定分类的提示词。

### 3.3. FRD-3: 内置AI工具

*   **需求描述:** 在AI助手面板中提供如“扩写”、“缩写”等快捷按钮，方便用户进行常用操作。
*   **功能点:**
    *   **3.3.1 (后端):** 在 `prompts` 表中预置一批 `IsSystem` 为 `true` 的系统级提示词，用于实现这些内置功能。
    *   **3.3.2 (后端):** `/api/generate` 接口需要能正确处理当请求中包含 `prompt_id` 时的逻辑。
    *   **3.3.3 (前端):** AI助手UI中的“扩写”、“缩写”等按钮，在点击时应携带对应的系统 `prompt_id` 调用生成接口。
