# 章节系统当前进展与下一步计划

## 当前任务背景

本任务围绕 `work-man-ui` 的章节系统重构展开，目标是把原有偏“管理后台式”的章节页面，重构为以目录、正文、分析和片段选择为核心的章节工作区。

当前已完成的工作，主要集中在“交互骨架”和“最小可运行工作流”的建立，而非最终产品完成态。

## 当前实现的真实边界

### 已经真实存在的能力

- 章节目录页骨架
- 单章节阅读工作区
- 单章节编辑工作区
- 导出入口
- 分析面板 / sheet
- 片段选择模式
- 大纲 / 角色结果展示
- 整章与片段分析类型切换

### 仍然是最小实现 / 未完成的部分

- 分析结果目前仍是本地最小生成逻辑，不是真实后端或 AI 异步提取结果
- 章节目录页的分卷树、折叠、定位能力还没完整实现
- 编辑态和阅读态虽然共享了工作区语义，但还未深度统一到底层状态管理
- 构建链和类型链尚未整体收口

## 下一步推荐计划

### 方向 A：继续产品层推进（推荐）

目标：把当前“本地同步生成结果”的分析工作区升级为更真实的异步分析流。

建议步骤：

1. 为分析工作区补 `loading / success / error / retry` 状态
2. 将当前同步 `buildChapterAnalysisResult` 调用替换为最小异步分析流程
3. 在阅读态和编辑态统一异步分析状态管理
4. 为移动端分析 sheet 补专门测试

### 方向 B：工程收口

目标：把当前章节系统改造从“局部测试通过”推进到“整体可构建”。

建议步骤：

1. 回到 `frontend` 级别继续清理 `pnpm build` 暴露的问题
2. 逐个处理 TypeScript 与环境阻塞点
3. 在章节系统局部回归通过的基础上，再做整体 build 验证

## 我推荐的下一步

建议优先继续 **方向 A**：

- 先让分析工作区具备真正的异步状态语义
- 因为这会把章节系统从“交互骨架阶段”推进到“真实产品行为阶段”
- 然后再统一做工程收口，会更顺畅
