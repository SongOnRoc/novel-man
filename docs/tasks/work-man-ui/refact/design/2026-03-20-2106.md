# 章节系统与现有代码结构映射

## 目的

在统一设计方案基础上，进一步回答一个实现前必须明确的问题：

- 当前已有的章节相关页面，哪些可以保留？
- 哪些需要重写？
- 哪些应该改角色？
- 新设计如何映射到现有路由结构？

本文件只做结构映射，不进入代码实现细节。

## 一、现有章节相关页面盘点

### 1. 目录页

- `frontend/src/app/(main)/works/[id]/chapters/page.tsx`
- 当前角色：章节管理页
- 当前特征：
  - `PageHeader`
  - 排序切换
  - 洞察卡片
  - 章节列表
  - 分页
  - 导入 / 重排对话框

### 2. 默认章节详情路由

- `frontend/src/app/(main)/works/[id]/chapters/[chapterId]/page.tsx`
- 当前角色：纯重定向路由
- 当前行为：直接跳转到 `preview`

### 3. 章节预览页

- `frontend/src/app/(main)/works/[id]/chapters/[chapterId]/preview/page.tsx`
- 当前角色：阅读 / 导出页
- 当前特征：
  - 独立 `PageHeader`
  - 返回章节列表 / 返回编辑
  - 导出能力
  - 正文预览

### 4. 章节编辑页

- `frontend/src/app/(main)/works/[id]/chapters/[chapterId]/edit/page.tsx`
- 当前角色：正文编辑页
- 当前特征：
  - 基于 `TiptapEditor`
  - 自动保存
  - 返回作品

### 5. 旧列表组件

- `frontend/src/app/(main)/works/[id]/chapters/components/TOCChapterList.tsx`
- `frontend/src/app/(main)/works/[id]/chapters/components/chapter-list.tsx`

其中：

- `TOCChapterList.tsx` 是当前仍在使用的章节列表视图。
- `chapter-list.tsx` 更像旧版表格组件，已不符合新方向，应视为遗留组件。

## 二、与新结构的映射关系

统一设计里的四个单元是：

- 章节目录页
- 单章节页
- 分析工作区
- 段落选择模式

映射到现有代码后，建议如下。

### 1. `chapters/page.tsx` 保留路由，但必须重写页面身份

- 路由保留：`/works/[id]/chapters`
- 新角色：章节目录页
- 不再是章节管理后台页

#### 应保留的能力

- 加载当前作品章节数据
- 目录级跳转
- 导入章节入口
- 少量目录级操作

#### 应移除或显著降级的部分

- `ChapterInsightCard` 这类洞察卡片
- 过重的顶部说明与动作堆叠
- 章节页内的大量“管理后台”语义
- 纯前端分页如果与目录定位冲突，需要重新评估

#### 应新增或替换的能力

- 卷 / 章树形结构
- 卷折叠逻辑
- 搜索与自动展开命中卷
- 当前章节定位高亮

### 2. `[chapterId]/page.tsx` 不应继续无脑重定向到 `preview`

- 当前行为：重定向到 `preview`
- 新建议角色：单章节默认入口

#### 推荐调整

- 将 `/works/[id]/chapters/[chapterId]` 直接变成“单章节页”的主入口。
- 页面内部再根据模式切换：
  - 阅读态
  - 编辑态
  - 分析态
  - 选择态

#### 原因

- 未来章节系统的主工作区应该聚焦在单章节页，而不是让默认入口先跳到一个独立 `preview` 子路由。
- 当前纯重定向会让结构碎裂，不利于承载目录、分析与片段选择的统一任务流。

### 3. `preview/page.tsx` 不应作为未来核心承载页

- 当前页面更适合视为旧的章节阅读实现。
- 未来它有两种可能：

#### 方向 A：降级为内部模式，不再保留独立路由（推荐）

- 把当前预览逻辑吸收进新的单章节页阅读态。
- 导出能力转为单章节页中的一个辅助动作。

#### 方向 B：保留为纯只读视图

- 仅当确实需要一个独立只读页面时才保留。
- 但它不应再承担未来目录与分析主链路。

#### 当前建议

- 优先走方向 A。
- 即：未来 `preview/page.tsx` 的主要代码逻辑应被并入单章节页的阅读态，而不是继续作为单独主页面存在。

### 4. `edit/page.tsx` 可保留为实现基础，但角色需要升级

- 当前页面是最接近正确方向的章节工作区基础。
- 其核心优势：
  - 已经基于 `TiptapEditor`
  - 已形成桌面 / 移动端不同容器承载的编辑器经验

#### 未来角色建议

- 不再只是“编辑子页”，而应成为“单章节页编辑态”的主要实现基础。

#### 需要补齐的能力

- 目录入口
- 分析工作区入口
- 进入段落选择模式的入口
- 与单章节阅读态的统一导航关系

#### 当前判断

- `edit/page.tsx` 适合保留其编辑器实现能力。
- 但它未来不应孤立存在，而应被纳入更统一的单章节工作区结构。

### 5. `TOCChapterList.tsx` 应保留思路，但重构为目录树组件

- 当前组件的定位还只是“章节列表视图”。
- 未来应升级为更明确的目录组件，例如：
  - `ChapterTocTree`
  - `VolumeChapterTree`

#### 可保留的部分

- 章节项的基本信息组织
- 跳转行为
- 行级菜单入口

#### 必须重构的部分

- hover 才出现关键操作
- 纯平铺章节列表
- 缺乏卷节点层级
- 缺乏搜索与高亮逻辑

### 6. `chapter-list.tsx` 应视为遗留实现，后续可移除

- 当前是旧式表格组件。
- 与目录页新方向不一致。
- 不建议继续复用。

## 三、推荐的新页面角色分配

### 1. 章节目录页

- 路由：`/works/[id]/chapters`
- 页面职责：结构管理与跳转

### 2. 单章节页

- 路由：`/works/[id]/chapters/[chapterId]`
- 页面职责：阅读 / 编辑 / 分析主入口

### 3. 章节编辑具体实现

- 现有：`/works/[id]/chapters/[chapterId]/edit`
- 新建议：
  - 短期可以保留
  - 长期应考虑并入单章节页内部模式，避免阅读态和编辑态路由割裂过重

### 4. 章节预览具体实现

- 现有：`/works/[id]/chapters/[chapterId]/preview`
- 新建议：
  - 不再作为未来主链路中心
  - 优先将其逻辑并入单章节页阅读态

## 四、迁移优先级建议

### 第一步：重写目录页身份

- 先改 `chapters/page.tsx`
- 目标：从管理后台页改成目录定位页

### 第二步：确立单章节主入口

- 再改 `[chapterId]/page.tsx`
- 目标：不再默认重定向，而是成为真正的单章节页入口

### 第三步：吸收预览页逻辑

- 将 `preview/page.tsx` 的正文阅读与导出逻辑吸收到单章节页阅读态

### 第四步：升级编辑页能力

- 基于现有 `edit/page.tsx` 和 `TiptapEditor`，补目录入口、分析入口、选择模式入口

### 第五步：重构目录组件

- 用新目录树组件替代 `TOCChapterList.tsx` 当前的平铺列表语义

## 五、结论

当前章节相关路由并不是完全推翻重来，而是要重新分配角色：

- `chapters/page.tsx` 保留路由，重写身份
- `[chapterId]/page.tsx` 从跳转页升级为单章节主入口
- `preview/page.tsx` 降级为可吸收的旧阅读实现
- `edit/page.tsx` 保留编辑基础，但并入统一章节工作区逻辑
- `TOCChapterList.tsx` 保留部分信息组织思路，但必须升级为真正目录组件

这样做的好处是，既能利用现有编辑器资产，也能避免继续在错误的章节页结构上修修补补。
