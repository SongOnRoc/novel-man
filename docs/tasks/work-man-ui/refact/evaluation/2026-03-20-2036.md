# UI 结构性问题深度评估

## 评估目的

本次评估聚焦当前前端 UI 的结构性问题，不再停留于“是否有响应式类名”或“布局是否能缩放到手机”这类表面判断，而是直接评估：

- 页面是否围绕明确主任务设计。
- 信息层级是否合理。
- 交互模型是否适合 PC 与移动端。
- 哪些现有模式必须停止复用。

## 核心结论

当前 UI 的主要问题不是“移动端适配不够精细”，而是很多页面从产品结构上就不成立：

- 页面过度服务展示，而不是服务行动。
- 低价值信息占据了高价值屏幕资源。
- 模块感压过任务感。
- 大量页面没有真正的主次和状态切换设计。

因此，移动端体验差并不是孤立问题，而是错误页面结构在小屏上的放大。

## 一、当前最严重的问题模式

### 1. 用展示型首页思维代替任务型页面思维

- 关键文件：`frontend/src/app/(main)/dashboard/page.tsx`、`frontend/src/app/(main)/works/page.tsx`
- 这些页面优先展示欢迎语、概览卡片、说明和模块入口，而不是优先把用户送到“继续当前工作”的动作。
- 这种设计在桌面端已经偏低效，在移动端会直接退化成大段低效滚动。

### 2. 把辅助上下文错误提升为主内容

- 关键文件：
  - `frontend/src/app/(main)/dashboard/page.tsx:81`
  - `frontend/src/app/(main)/works/page.tsx:109`
  - `frontend/src/app/(main)/works/[id]/page.tsx:160`
  - `frontend/src/app/(main)/works/[id]/chapters/page.tsx:313`
- 总字数、章节数、最近更新、排序状态、作品 ID 等信息本质上是辅助上下文，不应该一项一个大卡片占据页面核心位置。
- 特别是在移动端，这类设计会让首屏充满“知道了也不能立刻行动”的内容。

### 3. 把单页面做成“模块说明页 + 操作页 + 摘要页”的混合体

- 关键文件：`frontend/src/app/(main)/works/[id]/page.tsx`
- 当前单作品工作台不是一个真正的工作区，而更像一个功能地图。
- 用户只是想继续章节、草稿或编辑任务，却需要先穿过封面、状态、统计、模块切换、摘要块。

### 4. 章节页的页面身份定义错误

- 关键文件：`frontend/src/app/(main)/works/[id]/chapters/page.tsx`
- 当前章节页虽然叫“章节目录”，但结构上更像管理后台页面：标题、说明、动作、排序、洞察卡、列表、分页、对话框全部堆叠。
- 这种页面结构无法自然承载未来的：
  - 分卷目录
  - 目录折叠
  - 大规模章节定位
  - 单章节分析入口
  - 段落级提取

### 5. 把 hover 交互当成默认交互模型

- 关键文件：`frontend/src/app/(main)/works/[id]/chapters/components/TOCChapterList.tsx:75`
- 关键操作依赖 hover 出现，在桌面端尚可，在移动端会变成“操作可用但不显眼”。
- 这说明很多组件的交互出发点仍然是桌面鼠标环境，而不是通用触屏环境。

## 二、为什么草稿编辑链路相对成立

### 1. 它只服务一个主任务

- 关键文件：`frontend/src/features/editor/components/TiptapEditor.tsx`
- 编辑器页面知道自己的主角是正文，因此没有让统计、说明、模块导航与编辑区争夺主空间。

### 2. 它采用的是“同一任务流，不同承载容器”

- 桌面端：侧边面板承载 AI / 搜索等辅助能力。
- 移动端：`Sheet`、移动 AI 容器承载相同能力。
- 这是合理的跨端策略：换容器，不换产品逻辑。

### 3. 它承认移动端有真实物理限制

- 关键文件：`frontend/src/features/editor/components/TiptapEditor.tsx:575`
- 已处理底部安全区、浮层、搜索面板等问题。
- 说明这条链路已经从“缩桌面页面”进化到“承认移动端是不同使用环境”。

## 三、必须废弃的 UI 模式

### 1. 首屏统计卡铺满

- 几个辅助数字各占一个大卡片，尤其是在移动端，占空间却不能直接帮助用户行动。

### 2. 工作台式展示首页

- 先展示系统能力、模块地图、概览，再让用户找真正要做的事情。

### 3. 长工具栏加多按钮换行

- 按钮换行不是移动端体验优化，只是把拥挤从横向改成纵向。

### 4. hover 才出现关键操作

- 关键操作必须默认可发现，不能建立在 hover 之上。

### 5. 在一个页面里并列堆目录、说明、统计、正文、分析

- 这会让页面没有状态，也没有主次。

## 四、可以保留和复用的模式

### 1. 单主任务页面骨架

- 先定义主任务，再决定哪些能力退为辅助层。

### 2. `panel` 与 `sheet/dialog` 的容器切换

- 桌面端与移动端可以承载方式不同，但核心任务流保持一致。

### 3. 列表信息在不同端做不同组织，但不改业务逻辑

- 例如 `DraftList` 的思路比大多数页面更接近正确方向。

### 4. 显式状态切换

- 浏览态、选择态、分析态、编辑态应被清楚地区分，而不是平铺混合。

## 五、对章节系统的直接启示

后续章节系统不应继续沿用当前工作台式页面组织方式。更合理的职责分工应是：

- 章节目录页：结构浏览、分卷折叠、定位与跳转。
- 单章节页：阅读或编辑正文。
- 分析能力：作为单章节页的辅助工作区。
- 段落级提取：进入显式选择模式，而不是与正文长期并列展示。

否则，章节系统只会成为另一个“功能很多但页面很重”的展示型工作台。
