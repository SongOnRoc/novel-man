# 章节系统跨端 UI 全局评估

## 评估背景

本次评估不再从“是否用了响应式类名”出发，而是从更本质的维度判断当前 UI 是否成立：

- 页面目标是否清晰。
- 信息层级是否失真。
- 交互模型是否自洽。
- PC 与移动端的差异是必要适配，还是错误布局被强行压缩后的结果。

当前最大的问题不是“移动端适配不够精细”，而是很多页面从产品结构上就不合理：把低价值信息做成高权重展示，把桌面端的展示欲误当成产品组织能力，导致页面在 PC 上已经偏笨重，在移动端则直接失真。

## 一、核心诊断：当前 UI 的根问题不在样式，而在页面思维

### 1. 很多页面不是为“完成任务”设计的，而是为“展示模块完整性”设计的

- 关键文件：
  - `frontend/src/app/(main)/dashboard/page.tsx`
  - `frontend/src/app/(main)/works/page.tsx`
  - `frontend/src/app/(main)/works/[id]/page.tsx`
- 这些页面共同的问题是：首先展示一大块欢迎语、概览、统计、模块入口、说明文案，再让用户去做真正的事。
- 这会导致页面首屏看起来热闹，但任务启动很慢。用户不是来欣赏系统有多少模块，而是来继续创作、进入章节、打开草稿、处理当前上下文。

### 2. 低价值信息被错误提升为主视觉内容

- 关键文件：
  - `frontend/src/app/(main)/dashboard/page.tsx:81`
  - `frontend/src/app/(main)/works/page.tsx:109`
  - `frontend/src/app/(main)/works/[id]/page.tsx:160`
  - `frontend/src/app/(main)/works/[id]/chapters/page.tsx:313`
- 总字数、章节数、最近更新、作品 ID、排序状态、关联状态等，大多属于辅助上下文，不应该在移动端一项一个大卡片占据主页面。
- 这类设计的问题不是“卡片太大”，而是它们根本不配拥有首屏资源。

### 3. 当前很多页面把“知道一些信息”和“做一件事”混在同一层

- 用户要完成的任务，通常只有一个主目标：
  - 进入作品
  - 打开草稿
  - 查看目录
  - 编辑章节
- 但页面同时塞入：说明、概览、统计、动作、模块切换、占位信息、未来计划，导致用户无法快速判断当前页面最重要的动作是什么。

### 4. 许多所谓“移动端问题”，本质上是桌面页面本身就没有强主线

- 如果桌面端页面本身是“概览 + 统计 + 模块 + 内容 + 次级入口”的混合体，那么移动端不管怎么缩、怎么换行、怎么单列，都会很难用。
- 所以不能把当前问题定义为“PC 合理、移动端不合理”；更准确地说，是“PC 端很多页面也只是看起来完整，实际并不高效”。

## 二、按页面族看：当前最严重的结构性问题

### 1. Dashboard 和作品库页是典型的“视觉工作台”，不是“行动工作台”

#### 1.1 Dashboard 页的问题

- 文件：`frontend/src/app/(main)/dashboard/page.tsx`
- 问题本质：它假设用户需要一套“创作者驾驶舱”，但当前产品真正高频的行为其实不是浏览总览，而是继续当前创作。
- 具体表现：
  - 欢迎语占首屏，但对 returning user 几乎没有价值。
  - 统计卡被赋予过高视觉权重，却不能直接帮助推进任务。
  - 最近作品列表与快捷操作被放在统计体系之后，任务路径反而被概览信息压后。
- 在移动端，这会退化成一整屏“你有多少作品/章节/草稿”的陈列柜，像一块仪表盘，而不是写作入口。

#### 1.2 作品库页的问题

- 文件：`frontend/src/app/(main)/works/page.tsx`
- 问题本质：把“作品列表页”做成了“作品品牌页 + 说明页 + 统计页 + 列表页”的合体。
- 最不合理的地方：右侧三个 `SummaryPanel` 这种结构，在移动端会变成连续三个大卡片，几个辅助数字占据极高屏幕成本，却没有帮助用户更快进入某部作品。
- 这属于典型的“为了显得完整而堆出完整感”，但没有遵守列表页最基本的原则：列表页的主任务应该是查找、识别、进入目标对象。

### 2. 单作品工作台是“功能地图”，不是“实际工作区”

- 文件：`frontend/src/app/(main)/works/[id]/page.tsx`
- 当前页面的问题不只是信息多，而是它试图同时承担：
  - 作品总览
  - 模块导航
  - 章节摘要
  - 草稿摘要
  - 资产模块占位
- 这类页面在产品上最容易变成“每个模块都沾一点，但没有任何模块真正好用”。
- 特别是移动端：
  - 作品封面占位、状态徽章、4 个 QuickStat、Tabs 区、章节列表预览、草稿列表预览会形成很长的前置滚动。
  - 用户往往只是想“继续上次工作”，却被迫先穿过一个作品介绍页。

### 3. 章节页现在是“章节管理说明页”，不是“目录页”

- 文件：`frontend/src/app/(main)/works/[id]/chapters/page.tsx`
- 这页当前最大的误区是：名义上在做章节目录，实际在做一个管理后台式页面。
- 页面结构是：
  - PageHeader
  - 顶部动作区
  - 排序切换
  - 4 个洞察卡片
  - 章节列表
  - 分页
  - 导入 / 重排对话框
- 这套结构根本不适合未来的目标：
  - 分卷目录
  - 卷折叠
  - 数千章节定位
  - 单章节分析入口
  - 跨端使用
- 真正的问题不是“要不要优化章节卡片”，而是这一页的页面身份从一开始就定义错了。

### 4. 世界观页和大纲页是桌面工作台模型，移动端几乎天然不成立

- 文件：
  - `frontend/src/app/(main)/works/[id]/world/page.tsx`
  - `frontend/src/app/(main)/works/[id]/outline/page.tsx`
- `world` 直接建立在左右分栏的工作台假设上，`outline` 直接建立在横向看板假设上。
- 它们不是简单“没做好移动端”，而是其核心交互模型天然更偏向大屏。
- 如果继续把章节分析也套到这种模式里，移动端一定继续崩。

### 5. 很多列表页虽然 technically 响应式，但没有真正的移动端交互重构

- 文件：
  - `frontend/src/app/(main)/works/[id]/drafts/page.tsx`
  - `frontend/src/app/(main)/works/[id]/characters/page.tsx`
  - `frontend/src/features/drafts/components/DraftList.tsx`
  - `frontend/src/app/(main)/works/[id]/chapters/components/TOCChapterList.tsx`
- `DraftList` 已经比其他列表成熟，因为它至少意识到：桌面和移动的信息组织应该不同。
- 但像 `TOCChapterList` 这种组件仍大量依赖 `group-hover` 才显操作，说明它的默认交互模型仍是桌面 hover 优先。
- 这类组件放到手机上，即便视觉上能排下，也并不意味着操作路径自然。

## 三、真正相对成立的模式：为什么草稿编辑是例外

### 1. 它承认页面只能有一个主角：正文

- 文件：`frontend/src/features/editor/components/TiptapEditor.tsx`
- 编辑器页面的核心目标非常单纯：写内容。
- 搜索、AI、设置、标题、返回都围绕这个主任务展开，没有试图让统计信息、模块说明、概览卡片和正文争首屏。

### 2. 它做的是“容器适配”，不是“产品逻辑分叉”

- 桌面端：正文 + 侧边能力面板。
- 移动端：正文 + 底部 `Sheet` / 移动 AI 容器。
- 这里的跨端策略是对的：
  - 任务流一致。
  - 状态一致。
  - 展示容器不同。
- 这也是后续章节分析最应该复用的思路。

### 3. 它开始真正考虑小屏空间的物理限制

- 有底部安全区处理。
- 有浮动工具与正文阅读区的避让。
- 有移动端专属搜索承载方式。
- 换句话说，它不是在“缩桌面 UI”，而是在承认移动端是一种不同的使用环境。

## 四、当前 UI 最致命的模式性错误

### 1. 把“展示系统能力”放在“帮用户继续工作”之前

- 这是当前几乎所有工作台类页面的共同病灶。
- 系统好像总在告诉用户“我这里有这些模块、这些统计、这些上下文”，却没有尽快把用户送到他真正想做的下一步。

### 2. 把上下文当主内容，把主内容当模块之一

- 例如作品页里，作品概览、封面、徽章、统计卡的视觉权重很高。
- 但用户真正关心的可能只是：
  - 最近在写哪章
  - 哪篇草稿没发布
  - 进入目录
- 这说明页面主次完全反了。

### 3. 将“模块导航”设计成页面主体，而不是服务任务的入口

- `Tabs`、模块 chips、管理占位块这些东西被设计得很显眼。
- 但它们只是去往别处的入口，不应该压过当前任务内容本身。

### 4. 视觉密度高，不代表信息效率高

- 当前很多页面看起来内容很丰富，但其实大量是：
  - 可有可无的说明
  - 可后置的统计
  - 占位性的未来能力描述
  - 语义重复的上下文卡片
- 这些内容会让页面显得“有东西”，但不会让页面更好用。

### 5. 当前 UI 缺少真正的状态设计

- 页面里很多能力是并排堆在一起，而不是被组织成明确状态：
  - 浏览态
  - 定位态
  - 选择态
  - 编辑态
  - 分析态
- 缺少状态设计的结果就是，所有能力都想常驻，最后全部挤爆页面。

## 五、面向后续设计的统一原则

### 1. 页面必须先回答：用户来这里最想完成什么

- 如果答不出来，就不应该开始设计布局。

### 2. 移动端首屏只允许出现主任务相关内容

- 统计、说明、辅助上下文默认降级。
- 不允许再出现“几个数字一项一个大卡片占满首屏”的设计。

### 3. 辅助能力必须后置或收纳

- 目录、筛选、统计、分析、设置等，不应默认和主内容并列争空间。
- 合适的承载形式包括：抽屉、sheet、dialog、折叠区、次级页面。

### 4. 不维护两套产品，只维护一套任务流

- 桌面和移动端可以换容器，但不能换主逻辑。
- 也就是说，允许“panel vs sheet”，不允许“桌面有这能力，移动没有”。

### 5. 复杂页面要用“模式切换”而不是“区域堆叠”解决复杂度

- 例如：
  - 浏览目录态
  - 片段选择态
  - 分析结果态
- 不要把这些状态同时平铺在一个页面里。

### 6. 所有 hover 才出现的关键操作都应该被视为风险设计

- 关键操作必须在移动端可发现、可触达、可单手完成。

### 7. 长列表与长目录不能靠连续滚动硬扛

- 必须有折叠、过滤、搜索定位、局部展开、虚拟滚动等机制。

## 六、对章节系统的直接结论

### 1. 章节页不能继续沿用当前“工作台首页”思路

- 不能再做成：标题 + 说明 + 卡片 + 按钮 + 列表 + 更多卡片。
- 这条路继续走，只会把目录、分析、分卷、片段提取都堆成一个更重的管理后台页。

### 2. 章节系统必须拆职责

- 章节目录页：负责结构浏览、折叠、定位、跳转。
- 单章节页：负责阅读/编辑。
- 分析能力：作为单章节页的辅助工作区，而不是章节目录页的常驻区。
- 片段提取：必须进入显式选择模式。

### 3. 章节系统要复用草稿编辑的正确思路

- 一套任务流。
- 桌面端用侧边分析面板。
- 移动端用全屏 sheet / dialog。
- 不做两套完全不同的 UI。

## 七、结论

当前 UI 最大的问题不是“有些页面移动端不够精细”，而是：

- 页面过度服务展示，而不服务行动；
- 低价值信息占据高价值空间；
- 模块感压过任务感；
- 很多页面没有真正的主次和状态；
- 因而在移动端全面失真。

如果要继续推进章节系统、角色提取、大纲提取、段落级分析，必须先停止复用当前这些“工作台展示页”的组织方式，转向更明确的任务型页面设计。
