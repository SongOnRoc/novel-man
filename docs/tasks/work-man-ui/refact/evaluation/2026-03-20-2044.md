# UI 模式取舍清单

## 目的

在重新设计章节系统之前，先明确当前前端里哪些 UI 模式必须停止复用，哪些模式可以保留并抽象成通用能力。否则后续即使单页设计得更好，也会被旧的页面组织方式重新拖回“展示型工作台”。

## 一、必须废弃的 UI 模式

### 1. 首屏统计卡铺满

- 典型位置：`frontend/src/app/(main)/dashboard/page.tsx`、`frontend/src/app/(main)/works/page.tsx`、`frontend/src/app/(main)/works/[id]/page.tsx`
- 问题：把总字数、总章节、最近更新、作品 ID 之类的JI辅助上下文做成首屏主角。
- 结论：这类信息在桌面端也应该降级，在移动端默认不应独占完整卡片区域。

### 2. 页面先讲系统能做什么，再让用户做事

- 典型位置：`frontend/src/app/(main)/dashboard/page.tsx`、`frontend/src/app/(main)/works/[id]/page.tsx`
- 问题：欢迎语、模块导览、能力说明、上下文摘要排在真正任务入口之前。
- 结论：继续创作、进入章节、打开草稿这类动作必须前置，系统介绍与说明必须后置。

### 3. 工作台首页承载过多模块预览

- 典型位置：`frontend/src/app/(main)/works/[id]/page.tsx`
- 问题：单作品首页同时承担作品介绍、模块导航、章节摘要、草稿摘要、资产占位，导致没有主任务。
- 结论：单作品首页不应再做“功能地图”，应改为任务入口页或最近工作恢复页。

### 4. 长工具栏 + 多按钮自动换行

- 典型位置：`frontend/src/app/(main)/works/[id]/chapters/page.tsx`、`frontend/src/app/(main)/works/[id]/drafts/page.tsx`
- 问题：按钮换行只是拥挤的另一种形式，不能解决主次混乱。
- 结论：移动端操作需要重组为主操作 + 更多操作菜单，桌面端也要减少同层级按钮数。

### 5. hover 才出现关键操作

- 典型位置：`frontend/src/app/(main)/works/[id]/chapters/components/TOCChapterList.tsx`
- 问题：依赖 hover 显示编辑、更多菜单、拖拽提示，移动端可发现性极差。
- 结论：关键操作必须显式可见，至少通过固定菜单入口暴露。

### 6. 在同一页面并列堆放多种状态

- 典型位置：`frontend/src/app/(main)/works/[id]/chapters/page.tsx`
- 问题：把说明、统计、列表、分页、导入、重排、后续分析能力都放在一个平面里。
- 结论：必须拆成浏览态、选择态、操作态、分析态等显式模式，不再平铺并列。

### 7. 以“能滚动”为前提的长页面设计

- 典型位置：`frontend/src/app/(main)/works/page.tsx`、`frontend/src/app/(main)/works/[id]/outline/page.tsx`
- 问题：默认假设用户愿意穿过很长页面去找任务入口。
- 结论：滚动只能承载内容，不应承载导航和任务发现的主逻辑。

### 8. 章节页沿用后台管理页思路

- 典型位置：`frontend/src/app/(main)/works/[id]/chapters/page.tsx`
- 问题：章节页现在更像操作面板，不像目录系统。
- 结论：后续章节页必须彻底转向目录与定位逻辑，不能继续追加卡片和说明块。

## 二、可以保留和复用的 UI 模式

### 1. 单主任务页面骨架

- 典型位置：`frontend/src/features/editor/components/TiptapEditor.tsx`
- 价值：页面知道自己的主角是谁，其他能力都退到辅助层。
- 复用方向：章节阅读页、章节编辑页、章节分析页都应遵守这一点。

### 2. 同一任务流，不同容器表现

- 典型位置：`frontend/src/features/editor/components/TiptapEditor.tsx`
- 价值：桌面端使用侧边面板，移动端使用 `Sheet` / 全屏容器，但核心逻辑不变。
- 复用方向：章节目录、章节分析、段落选择后的结果展示都应使用这个策略。

### 3. 列表内容按终端重组，但不改变业务行为

- 典型位置：`frontend/src/features/drafts/components/DraftList.tsx`
- 价值：桌面端和移动端信息排列不同，但编辑、发布、删除行为一致。
- 复用方向：目录列表、章节列表、角色列表都可以采用这种“信息重排，不改逻辑”的模式。

### 4. 辅助能力后置

- 典型位置：编辑器搜索、AI 面板
- 价值：主任务不被侧能力打断，用户按需展开。
- 复用方向：目录筛选、分析结果、批量操作、更多菜单都应后置承载。

### 5. 显式模式切换

- 典型位置：编辑器的搜索打开态、AI 打开态
- 价值：当某个能力开启时，用户知道自己进入了另一个工作模式。
- 复用方向：章节目录态、段落选择态、分析结果态应有明确边界。

## 三、对章节系统的约束

### 1. 章节目录页只能服务结构管理

- 核心任务：浏览卷章结构、搜索定位、折叠展开、跳转。
- 不再承载大量说明卡片、上下文统计卡、未来能力占位。

### 2. 单章节页只能服务内容处理

- 核心任务：阅读、编辑、切换章节、进入分析。
- 目录是辅助入口，不是长期并列在正文旁边的第二主角。

### 3. 分析能力只能作为辅助工作区存在

- 大纲提取、角色提取、段落级提取结果都必须后置承载。
- 桌面端适合右侧分析面板，移动端适合全屏 `Sheet` / `Dialog`。

### 4. 段落级提取必须进入显式选择模式

- 不能让用户在普通阅读态里一边读一边承担隐性多选逻辑。
- 进入选择模式后，页面才切换为“选择片段 -> 执行提取 -> 查看结果”的任务流。

## 四、结论

后续如果还沿用“展示型工作台 + 大卡片 + 说明块 + 多按钮 + 列表”的模式，章节系统一定继续失控。

真正应该延续的，不是这些表层布局，而是编辑器页面体现出的三个原则：

- 主任务单一
- 辅助能力后置
- 跨端只换容器，不换逻辑
