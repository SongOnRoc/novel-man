## 移动端布局专项评估

## 结论

- 当前移动端目录页不是“完全崩坏”，但也绝对谈不上合理。
- 你的判断是对的：页面存在“整个卡片内容不多，却在手机首屏占了很大面积”的问题。
- 这类问题不是单个控件尺寸失控，而是页面结构把 `PageHeader`、操作按钮、外层大卡片、工具条卡片、树节点卡片层层叠加，导致移动端首屏浪费严重。

## 依据

1. 页头在移动端垂直堆叠，且动作区不收敛
   - `frontend/src/components/common/layout/PageHeader.tsx:36`
   - 在 `sm` 以下为纵向堆叠，标题、描述、返回按钮、操作按钮会连续向下展开。
   - `frontend/src/app/(main)/works/[id]/chapters/page.tsx:410` 处又给了两个主操作：`导入章节`、`新建章节草稿`。
   - 在手机首屏里，这一段本身就已经比较高。

2. 页头下方又包了一层无实质信息增益的大容器卡片
   - `frontend/src/app/(main)/works/[id]/chapters/page.tsx:430`
   - 这里用了 `rounded-2xl border ... p-4 md:p-6` 的整块容器，把工具条、目录树、分页全部再包一层。
   - 对桌面端这是常见视觉分组，但对移动端会进一步制造“大块留白 + 多层边框”的笨重感。

3. 工具条本身又是一个独立卡片
   - `frontend/src/features/chapters/components/ChapterDirectoryToolbar.tsx:25`
   - 搜索框和控制按钮被放进第二层 `rounded-2xl border ... p-3` 容器。
   - 也就是说，手机上用户先看到一层大卡片，内部再嵌一个工具条卡片，内容却只有一个搜索框和 1 到 3 个按钮，信息密度明显偏低。

4. 树模式下每个分卷又是独立卡片，章节项还是卡片
   - 分卷容器：`frontend/src/features/chapters/components/ChapterTocTree.tsx:129`
   - 章节项容器：`frontend/src/features/chapters/components/ChapterTocTree.tsx:43`
   - 这导致移动端视觉上是“三层卡片套娃”：页面卡片 -> 工具条卡片 / 分卷卡片 -> 章节卡片。
   - 当章节内容只有“序号 + 标题 + 字数 + 更多操作”时，这样的包装明显过重。

5. 章节项垂直空间利用率不高
   - `frontend/src/features/chapters/components/ChapterTocTree.tsx:44`
   - `px-4 py-3` 配合左侧 `h-9 w-9` 序号圆点、下方单独一行字数信息，导致每条目录项高度偏高。
   - 在手机上一屏可见章节数偏少，目录页最核心的“快速扫目录”效率受损。

## 判断

- 从“功能完整性”看，目录页已经达标。
- 从“移动端是否合理”看，当前实现不达标，至少不符合高频列表页应该追求的首屏效率和信息密度。
- 更准确地说，当前是“能用，但移动端视觉结构笨重”。

## 建议的整改方向

1. 移除章节目录页外层大卡片，改为更轻的 section 容器
2. 工具条在移动端取消独立描边卡片，直接并入页面流
3. 章节项改成更紧凑的 list row，而不是厚重 card
4. 分卷组保留分组感，但弱化描边和内边距，避免三层卡片嵌套
5. 将字数等次要信息压缩到同一行，减少单项高度

## 总结

- 现有评估文档关于“功能主线完成”的判断大体还站得住。
- 但关于“整体可构建”和“当前已经可视为完成”的表述，需要根据最新 `pnpm build` 失败结果收紧。
- 移动端布局问题确实存在，而且问题点很明确：不是内容少，而是容器过多、层级过重、每层都在吃首屏高度。
