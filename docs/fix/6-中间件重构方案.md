# 中间件重构方案：解决循环依赖并保持模块化

**目标：** 解决 `middlewares` 子包（如 `auth`, `resource`）与其父包 `middlewares` 之间的循环依赖问题，同时保持现有基于依赖注入和模块化注册的设计原则。

## 问题根源

当前的架构中，`auth` 和 `resource` 等子包在自己的 `init()` 函数中尝试向父包 `middlewares` 的全局注册表注册自己。这导致了 Go 的编译器无法解决的循环导入问题：

- `middlewares/auth` 导入 `middlewares` 来访问注册表。
- `middlewares` 导入 `middlewares/auth` 来初始化模块。

## 解决方案：引入初始化器接口

为了打破这种循环，我们将引入一个新的抽象层：`MiddlewareInitializer` 接口。这个接口将解耦中间件的 **创建** 和 **注册** 过程。

### 步骤 1：定义 `MiddlewareInitializer` 接口

在 `backend/internal/contracts/middlewares/middleware.go` 文件中，我们将定义一个新的接口：

```go
// MiddlewareInitializer 定义了中间件初始化器的接口
type MiddlewareInitializer interface {
	// Init 创建并返回一个中间件实例
	Init() (Middleware, error)
}
```

这个接口非常简单，它只要求实现者提供一个 `Init` 方法，该方法返回一个创建好的、符合 `Middleware` 接口的实例。

### 步骤 2：改造子包以实现新接口

我们将修改 `auth` 和 `resource` 包，让它们实现 `MiddlewareInitializer` 接口，而不是直接与注册表交互。

**示例：`backend/internal/middlewares/auth/auth.go`**

```go
package auth

import (
	// ... 必要的 imports
	"novel-man/backend/internal/container"
	"novel-man/backend/internal/contracts/auth"
	"novel-man/backend/internal/contracts/middlewares"
)

// ... AuthMiddleware 的实现保持不变 ...

// AuthMiddlewareInitializer 实现了 MiddlewareInitializer 接口。
type AuthMiddlewareInitializer struct {
	AuthService auth.AuthService
}

// NewAuthMiddlewareInitializer 通过依赖注入创建一个新的 AuthMiddlewareInitializer。
func NewAuthMiddlewareInitializer(authService auth.AuthService) middlewares.MiddlewareInitializer {
	return &AuthMiddlewareInitializer{AuthService: authService}
}

// Init 创建并返回一个 AuthMiddleware 实例。
func (i *AuthMiddlewareInitializer) Init() (middlewares.Middleware, error) {
	// 调用现有的 NewAuthMiddleware 函数来创建实例
	return NewAuthMiddleware(i.AuthService), nil
}

// 在包初始化时，将 Initializer 注册到 DI 容器中
func init() {
	container.Container.Provide(NewAuthMiddlewareInitializer)
}
```

**关键改动：**

1.  **移除旧的 `authMiddlewareModule`** 和相关的 `init()` 注册逻辑。
2.  **创建 `AuthMiddlewareInitializer`**，它通过依赖注入获取 `AuthService`。
3.  **实现 `Init()` 方法**，该方法简单地调用 `NewAuthMiddleware` 来返回一个中间件实例。
4.  **在 `init()` 函数中**，我们将 `NewAuthMiddlewareInitializer` 注册到 `dig` 容器中。这使得容器知道如何创建这个初始化器。
5.  对 `resource` 包执行类似的操作。

### 步骤 3：中央化注册

现在，子包只负责“声明”如何创建自己，而不再关心“何时”或“如何”被注册。注册的责任将完全由 `middlewares` 父包承担。

我们将修改 `backend/internal/middlewares/module.go`（或一个专门的初始化文件），使其从 `dig` 容器中获取所有 `MiddlewareInitializer` 的实现，并完成注册。

**示例：`backend/internal/middlewares/module.go`**

```go
package middlewares

import (
	"novel-man/backend/internal/container"
	"novel-man/backend/internal/contracts/middlewares"
	"go.uber.org/dig"
)

// ... MiddlewareProvider 和其他代码保持不变 ...

// InitMiddlewares 初始化所有中间件模块
func InitMiddlewares() error {
	// 定义一个参数结构体，告诉 dig 我们需要所有 MiddlewareInitializer 的实现
	type MiddlewareInitializers struct {
		dig.In
		Initializers []middlewares.MiddlewareInitializer `group:"middleware_initializers"`
	}

	return container.Container.Invoke(func(params MiddlewareInitializers) error {
		registry := GetMiddlewareRegistry()
		for _, initializer := range params.Initializers {
			middleware, err := initializer.Init()
			if err != nil {
				return err
			}
			registry.Register(middleware)
		}
		return nil
	})
}

// 为了让 dig 能够收集所有 Initializer，我们需要修改子包的 Provide 调用
// 示例：backend/internal/middlewares/auth/auth.go
func init() {
    // 使用 As 和 Group 选项告诉 dig 这是一个需要被收集的 Initializer
	container.Container.Provide(NewAuthMiddlewareInitializer, dig.As(new(middlewares.MiddlewareInitializer)), dig.Group("middleware_initializers"))
}
```

**关键改动：**

1.  **`InitMiddlewares` 函数** 现在使用 `dig.In` 和 `group` 标签从容器中“收集”所有被标记为 `"middleware_initializers"` 组的 `MiddlewareInitializer` 实例。
2.  **遍历并注册**：它遍历所有获取到的 `initializer`，调用它们的 `Init()` 方法来创建中间件实例，然后将实例注册到 `MiddlewareRegistry` 中。
3.  **更新 `Provide` 调用**：在 `auth` 和 `resource` 包的 `init` 函数中，我们需要更新 `Provide` 调用，使用 `dig.As` 和 `dig.Group` 来正确地将我们的 `Initializer` 注册到容器并添加到指定的组中。

## 优势

-   **消除循环依赖**：子包不再导入父包，彻底解决了编译问题。
-   **保持模块化**：每个中间件仍然在自己的包中定义和管理其依赖关系。
-   **遵循依赖倒置原则**：高层模块（`middlewares`）不依赖于低层模块（`auth`），它们都依赖于抽象（`MiddlewareInitializer` 接口）。
-   **自动化注册**：添加新的中间件只需要实现 `MiddlewareInitializer` 接口并将其注册到 `dig` 容器中，`InitMiddlewares` 函数会自动发现并注册它，无需手动修改。

这个方案在解决技术问题的同时，保留并优化了原有的架构设计。

## 应用模块使用方案

重构完成后，在各个应用模块（如 `auth`, `works` 等）中使用中间件的流程将非常清晰和统一。核心是通过依赖注入获取 `MiddlewareProvider`。

**示例：在 `backend/internal/apps/auth/module.go` 中应用 `auth` 中间件**

```go
package auth

import (
	// ...
	"novel-man/backend/internal/container"
	"novel-man/backend/internal/controllers/auth"
	"novel-man/backend/internal/middlewares" // 导入 middlewares 包
	// ...
	"github.com/gin-gonic/gin"
)

type authModule struct {
	// 在模块结构体中持有中间件提供者
	middlewareProvider *middlewares.MiddlewareProvider
}

// ... init 函数不变 ...

func (m *authModule) RegisterRoutes(router *gin.RouterGroup) {
	// 通过依赖注入获取 AuthController 和 MiddlewareProvider
	err := container.Container.Invoke(func(
		controller *auth.AuthController,
		provider *middlewares.MiddlewareProvider,
	) {
		// 将获取到的 provider 存储在模块实例中
		m.middlewareProvider = provider

		// ... 其他路由 ...

		// 需要认证的路由组
		authRequiredGroup := router.Group("/auth")
		
		// 从 provider 获取 "auth" 中间件
		authMiddleware, ok := m.middlewareProvider.Get("auth")
		if !ok {
			// 在实际应用中，这里应该记录一个严重错误，因为中间件应该总是可用的
			panic("auth middleware not found")
		}

		// 应用中间件
		authRequiredGroup.Use(authMiddleware.Handler())
		{
			authRequiredGroup.GET("/me", controller.GetCurrentUser)
			authRequiredGroup.POST("/logout", controller.Logout)
		}
	})
	if err != nil {
		panic(err)
	}
}
```

### 关键步骤

1.  **注入 `MiddlewareProvider`**：在模块的 `RegisterRoutes` 方法中，通过 `container.Invoke` 从 `dig` 容器获取 `*middlewares.MiddlewareProvider` 的实例。
2.  **获取中间件**：使用 `middlewareProvider.Get("middleware-name")` 方法来获取所需的中间件。例如，`Get("auth")` 获取认证中间件，`Get("ownership_work")` 获取作品所有权中间件。
3.  **应用中间件**：将获取到的中间件的 `Handler()` 应用到 Gin 的路由组或具体路由上。
4.  **错误处理**：如果 `Get` 方法返回的 `ok` 为 `false`，说明请求的中间件未被注册。在应用启动阶段，这通常是一个致命错误，应该立即 `panic` 以便开发者能快速定位问题。

此方案确保了应用模块与中间件的具体实现完全解耦，模块只关心需要“什么”中间件（通过名称），而不关心它“如何”被创建和管理。
