# 前后端数据对接需求文档 (Data Sync Spec)

**版本:** 1.0
**日期:** 2025-07-24

## 1. 概述

本文档旨在明确“网络小说作家作品管理系统”中，各核心模块在前后端数据同步方面的功能需求和用户故事。文档将作为后续技术设计与开发的基准，确保前后端团队对数据流、实体关系和业务逻辑有一致的理解。

本文档将重点关注以下待对接或待优化的模块：
- 角色管理 (Character Management)
- 世界观设定 (Worldbuilding)
- 草稿与章节 (Drafts & Chapters)
- 用户设置 (User Settings)
- AI 助手 (AI Assistant)

## 2. 核心设计原则

- **数据模型解耦:** 角色、世界观等核心创作元素应作为独立实体存在，与具体作品解耦，以支持跨作品复用。
- **清晰的状态转换:** 实体状态（如草稿到章节的转换）必须有明确、可靠的业务流程和技术实现。
- **统一的类型定义:** 前后端应遵循统一的数据结构定义，以减少数据不一致的风险。

## 3. 模块需求详述

### 3.1. 角色管理 (Character Management)

**目标:** 实现一个独立于作品的角色库，允许作者创建、管理并在不同作品中复用角色。

**用户故事:**

- **作为作者，我希望能创建一个角色库**，这样我就可以随时记录和丰富我的角色设定，而不用先创建一部作品。
- **作为作者，我希望能编辑和删除我的角色**，以便维护角色信息的准确性。
- **作为作者，我希望能在一个作品中“引用”我角色库里的角色**，而不是为每个作品都重复创建相同的角色信息。
- **作为作者，我希望能在一个作品中查看所有被引用的角色列表**，并能方便地跳转到他们的详细档案。

**功能需求:**

1.  **创建角色:** 用户可以在“工具”-“角色库”中创建新角色，角色信息不与任何`workId`绑定。
2.  **编辑/删除角色:** 用户可以修改或删除角色库中的任何角色。
3.  **角色与作品的关联:**
    -   应通过一个**中间表**（例如 `work_characters`）来管理角色和作品的多对多关系。
    -   在作品的特定管理界面（如“作品大纲”或“角色关系”页面），用户可以从角色库中选择角色，将其关联到当前作品。
    -   移除关联仅删除中间表的记录，不删除角色库中的角色实体。

### 3.2. 世界观设定 (Worldbuilding)

**目标:** 实现一个独立于作品的世界观设定库，允许作者创建、管理并在不同作品中复用世界观条目。

**用户故事:**

- **作为作者，我希望能建立一个通用的世界观知识库**，包含地点、组织、历史事件等，这样我就不必在每部小说里都重写一遍。
- **作为作者，我希望能对世界观条目进行分类管理**，例如“地理”、“种族”、“功法体系”等。
- **作为作者，我希望能在一个作品中引用这些世界观条目**，从而构建该作品独特的背景设定。

**功能需求:**

1.  **创建世界观条目:** 用户可以在“工具”-“世界观”中创建新条目，条目不与任何`workId`绑定。
2.  **分类管理:** 支持用户创建、重命名和删除世界观分类。
3.  **世界观与作品的关联:**
    -   与角色管理类似，应通过一个**中间表**（例如 `work_worldview_settings`）来管理世界观条目和作品的多对多关系。
    -   在作品的特定管理界面，用户可以从世界观库中选择条目，将其关联到当前作品。

### 3.3. 草稿与章节 (Drafts & Chapters)

**目标:** 明确`Draft`（草稿）和`Chapter`（章节）的定义、关系和转换流程。

**定义:**

-   **`Draft` (草稿):**
    -   是`Chapter`的一个**私有、未发布版本**。
    -   与特定作品关联 (`workId`)。
    -   包含标题和内容，但没有“顺序”、“发布状态”等公共属性。
    -   用户可以自由创建、编辑和删除，对读者不可见。
-   **`Chapter` (章节):**
    -   是作品的**公共、已发布内容**。
    -   拥有固定的发布顺序 (`order`) 和发布状态 (`status`)。
    -   一旦发布，其核心内容不应轻易修改，以保证读者阅读体验的一致性。

**转换流程:**

1.  **单向转换:** `Draft`可以**单向转换**为`Chapter`。
2.  **发布操作 (`Publish`):**
    -   用户在草稿管理界面执行“发布”操作。
    -   系统将该`Draft`的内容创建一个新的`Chapter`记录。
    -   新`Chapter`的顺序 (`order`) 默认排在当前作品的最后一章。
    -   发布成功后，原`Draft`记录应被**删除**。
    -   整个发布过程必须是**原子操作**，以防止数据不一致（例如，草稿删了但章节没创建成功）。
3.  **更新已发布章节:**
    -   原则上不鼓励直接修改已发布的`Chapter`。
    -   如需重大修改，推荐的流程是：将该`Chapter`的内容复制到一个新的`Draft`中进行编辑，完成后再用新内容“替换”或“更新”原`Chapter`。此流程的具体技术实现待定。

### 3.4. 用户设置 (User Settings)

**目标:** 定义需要同步的用户偏好设置项，提升个性化体验。

**功能需求:**

1.  **AI助手设置:**
    -   `ai_model`: 用户偏好的AI模型（例如 `gpt-4`, `claude-3`）。
    -   `custom_api_endpoint`: 自定义AI API的接入点URL。
    -   `api_key`: 自定义API的密钥（需加密存储）。
2.  **编辑器设置:**
    -   `editor_theme`: 编辑器的主题（例如 `light`, `dark`）。
    -   `font_size`: 编辑器默认字号。
    -   `line_height`: 编辑器默认行高。
3.  **数据同步:**
    -   所有设置项应在用户登录后从后端获取。
    -   修改后应立即同步到后端。

### 3.5. AI 助手 (AI Assistant)

**目标:** 定义AI助手需要对接的具体功能点和所需上下文。

**功能需求:**

1.  **文本润色 (`/ai/polish`):**
    -   **输入:** 一段选中的文本。
    -   **输出:** 经过润色和优化的文本。
2.  **内容续写 (`/ai/completion`):**
    -   **输入:** 当前光标前的部分文本作为引子。
    -   **上下文（Context）:** 为提高生成质量，API请求中应可选地包含以下上下文信息：
        -   `workId`: 当前作品ID。
        -   `chapterId`: 当前章节ID。
        -   `characterIds`: 当前章节或段落中出现的关键角色的ID。
        -   `worldviewSettingIds`: 相关的世界观设定ID。
        -   `stylePreference`: 用户的写作风格偏好（例如“简洁”、“华丽”）。
3.  **大纲生成 (`/ai/generate-outline`):**
    -   **输入:** 作品的简介或核心创意。
    -   **输出:** 一份结构化的小说大纲。
4.  **角色创建 (`/ai/create-character`):**
    -   **输入:** 对角色的简单描述（例如“一个失忆的剑客”）。
    -   **输出:** 一份包含姓名、背景、性格等详细信息的角色档案。
